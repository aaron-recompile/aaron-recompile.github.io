Builds on Christian Decker · eltoo

APO from scratch: a BIP-118 signer and an eltoo state chain

Two steps. First the primitive: an independent BIP-118 (ANYPREVOUT) signer, written outside Bitcoin Core's test framework and cross-validated by Inquisition's consensus code, with an on-chain proof that one signature spends two coins. Then the construction: a three-round eltoo state chain built on it and settled with OP_CHECKTEMPLATEVERIFY.

CodeDelving Bitcoin

The question

Eltoo, proposed by Christian Decker, Rusty Russell and Olaoluwa Osuntokun, lets a payment channel replace its state instead of punishing old states. Its enabling primitive is SIGHASH_ANYPREVOUT (BIP 118): a signature that does not commit to the coin it spends.

Bitcoin Core's wallet and command line cannot produce such a signature, so anyone who wants to exercise APO on Inquisition signet has to build the signer first. Following ajtowns' survey of CTV, APO and CAT activity on signet, this work adds that missing piece and then uses it end to end.

Part 1 · The primitive

A BIP-118 signer, cross-validated by consensus

The signing message Msg118 / Ext118 and the final TaggedHash("TapSighash", 0x00 || Msg118 || Ext118) are implemented in Python straight from the BIP, outside Bitcoin Core's test framework. Inquisition's C++ consensus code rebuilds the same digest from the transaction; if the two disagree by one byte, the transaction is rejected.

What BIP 118 changes is what the message leaves out:

FieldBIP 342 (SigMsg)BIP 118 (Msg118, 0x41)
nVersion, nLockTimeyesyes
sha_prevouts (which coins are spent)yesno
sha_sequencesyesno
input amount and scriptPubKeyyesyes
sha_outputsyesyes
tapleaf_hashyesyes
key_version0x000x01

On-chain proof: one signature, two coins

Two 50,000-sat UTXOs at the same address, under a single-leaf tapscript <0x01||xonly> OP_CHECKSIG. The first spend is signed; its whole witness (a 65-byte signature ending in 0x41, the 35-byte leaf, the 33-byte control block) is copied byte for byte onto a second transaction spending the other coin. Both confirmed in the same block. Changing the output address or amount in the second spend makes it fail: the input can be rebound, the destination cannot.

StepTransactionBlockNote
Spend A (signed)03c0577c…f3a4298280prevout 4b645108…:0
Spend B (witness copied, not re-signed)46091190…1a43298280prevout 543c97f7…:0

The outpoint drops out of the digest, and key_version 0x01 separates the signature domain so an APO signature cannot be replayed against an ordinary key.

Part 2 · The construction

A three-round eltoo state chain

With the signer in hand, every channel state becomes a three-leaf Taproot output. An APO update spends the current state and creates the next; the spent state's CTV leaf loses its only input and can never settle, so only the latest state can pay out. That is the eltoo invariant, executed end to end with current tooling.

each state UTXO (P2TR, three leaves)

  ctv_settle   <template_hash> OP_CHECKTEMPLATEVERIFY       # this state's payout
  apo_update   <0x01 || xonly_pubkey> OP_CHECKSIG          # next state replaces this one
  csv_escape   <2> OP_CHECKSEQUENCEVERIFY OP_DROP <pk> OP_CHECKSIG

fund -> v1 -> v2 -> v3   (two APO updates)
settle v3 through ctv_settle: witness = script + control block, empty stack

Check it yourself

The repository re-checks every claim on this page (no keys, no node: it recomputes the BIP-118 digest for every APO signature).

What it does not show

  • No Lightning protocol stack: no BOLT messaging, two-node exchange or HTLC routing.
  • The CSV timeout leaf is committed in every state but was not exercised.
  • One demo key signs every update; no FROST or MuSig2 aggregation.
  • Updates run sequentially; this is the execution layer underneath a channel, not a channel implementation.
